01

AI가 디버깅을 대신하는 것이 아닙니다

반복 조작을 줄이고, 가설 검증의 속도를 높입니다. 방향은 엔지니어가 잡습니다.

조작은 한 문장으로

창을 열고, 주소를 찾고, 명령을 입력하던 과정을 “지금 레지스터 보여줘” 한 문장으로 줄입니다.

가설 → 검증 루프

AI가 가설을 하나 세우고, 알맞은 스크립트를 골라 실행하고, 결과를 보고 다음 단계를 제안합니다.

팀 스크립트를 AI 도구로

이미 가진 PRACTICE(.cmm) 스크립트를 스킬로 등록하면, 서버 수정 없이 AI가 쓸 수 있는 도구가 됩니다.

예: 변수 counter를 누가 덮어쓰는지 찾기

기존 방식
  1. 심볼 창에서 counter 주소 확인
  2. 쓰기 브레이크포인트 설정
  3. 실행 → 정지
  4. 콜 스택·소스 확인, 메모
  5. 다음 쓰기를 찾아 2~4 반복
AI와 함께
“counter에 누가 값을 쓰는지 찾아줘”
mem_set_breakpoint (W)set_runningsw_get_stack_framesw_get_source

AI가 정지 지점마다 호출 경로와 소스를 정리하고, 계속 추적할지 묻습니다.

판단은 엔지니어가, 반복 조작은 AI가.

02

도구는 4개, 기능은 스크립트로

Lauterbach의 설계는 단순합니다. MCP 서버는 ‘스크립트를 실행하는 통로’만 제공하고, 실제 기능은 PRACTICE 스크립트가 담당합니다.

좌우로 밀어서 전체 구조를 보세요

AI가 매번 읽어야 하는 도구 목록은 4개로 고정되어 있습니다. 스크립트가 늘어나도 AI의 부담은 늘지 않습니다. 스킬은 한 벌 더 있지만(lauterbach-trace32-skill-creator) 스크립트 없이 작성 규칙만 담고 있어 실행 경로에는 나타나지 않습니다.

1
trace32_get_status

상태 확인

어떤 PowerView가 붙어 있고, 코어가 몇 개이며, 지금 실행 중인지 정지 상태인지 알려줍니다. 작업은 항상 여기서 시작합니다.

2
trace32_run_script

스크립트 실행

지정한 .cmm 스크립트를 인자와 함께 실행하고 결과까지 한 번에 돌려줍니다. 오래 걸리는 작업은 timeout을 올려 잡습니다.

3
trace32_run_command

단일 명령

어떤 스크립트도 다루지 않는 PRACTICE 명령 하나를 직접 실행합니다. 실행 범위 설정에 따라 꺼집니다.

4
trace32_manage_instances

인스턴스 관리

PowerView가 여러 개인 AMP 구성에서 대상 인스턴스를 더하거나 뺍니다. 단일 코어라면 쓸 일이 없습니다.

실행 범위에 따라 도구 수가 달라집니다 — 서버를 띄울 때 --execution-policy로 허용 범위를 반드시 정해야 합니다. strict는 2개(상태 확인·스크립트 실행), scripts는 3개, unrestricted는 4개를 제공합니다. 고르기 전에 10 안전하게 쓰기를 확인하세요.

Lauterbach가 제안하는 AI의 디버깅 방식

생각하는 동안 타깃은 멈춰 둔다추론은 정지 상태에서 하고, 필요한 만큼만 실행합니다.
관찰할 것을 먼저 정하고 실행한다브레이크포인트·트레이스를 먼저 설정하고 정해진 시간만 실행합니다.
리셋은 사람이 한다기본 스크립트에는 리셋 기능이 없습니다. 필요하면 AI가 사용자에게 요청합니다.

Lauterbach가 스킬 설명서(SKILL.md)에 담은 디버깅 지침을 요약했습니다.

5단계로 시작하기

완료한 단계는 체크해 두세요. 이 브라우저에 진행 상황이 남습니다.

진행 0 / 5
1

PowerView에서 Remote API 켜기

TRACE32 설정 파일(config.t32)에 아래 세 줄을 추가하고 PowerView를 다시 실행합니다. 다른 설정 블록과는 빈 줄로 구분합니다.

config.t32 
RCL=NETTCP
PORT=20000
REMOTEHOSTDENY

MDS 검증 환경 기준입니다. 포트를 20000이 아닌 값으로 쓰면 4단계 등록 명령에 --port를 추가합니다. REMOTEHOSTDENY는 Remote API를 이 PC 안으로 제한합니다 — 원격 접속이 꼭 필요한 경우가 아니면 반드시 넣으세요.

2

t32mcp와 스킬 내려받기

GitLab 릴리스 페이지에서 실행 파일을 받고, 저장소에서 스킬 두 벌을 가져옵니다.

  • 실행 파일 — t32mcp-windows-x86_64.exe 또는 t32mcp-linux-x86_64
  • 스킬 — 저장소 skills/ 아래 lauterbach-trace32-debug-basic과 lauterbach-trace32-skill-creator

실행 파일은 원하는 위치에 두면 됩니다. 이 가이드는 Windows C:\tools\t32mcp\, Linux /opt/t32mcp/를 예로 듭니다. 유지보수 라이선스가 있으면 t32chat의 스킬 페이지에서 매뉴얼·트레이스·RTOS 등 확장 스킬을 추가로 받을 수 있습니다.

4

AI 에이전트에 MCP 서버 등록

Claude Code 기준입니다. --skills에는 스킬 폴더들을 담고 있는 상위 폴더를 지정하고, --execution-policy로 허용 범위를 반드시 정합니다 — 빠뜨리면 서버가 실행되지 않습니다. 처음이라면 strict를 권합니다(10 안전하게 쓰기).

PowerShell · 명령 프롬프트 
cd C:\work\my-project
claude mcp add t32mcp -- C:\tools\t32mcp\t32mcp-windows-x86_64.exe --execution-policy strict --skills C:\work\my-project\.claude\skills
bash 
cd /home/me/my-project
chmod +x /opt/t32mcp/t32mcp-linux-x86_64
claude mcp add t32mcp -- /opt/t32mcp/t32mcp-linux-x86_64 --execution-policy strict --skills /home/me/my-project/.claude/skills

경로에 공백이 있으면 큰따옴표로 감싸세요. 모든 프로젝트에서 쓰려면 add 뒤에 -s user를 붙입니다. 등록과 스킬 배치는 AI 클라이언트가 켜질 때 한 번만 읽힙니다 — 작업을 마쳤으면 클라이언트를 다시 시작하세요. 디버깅 절차 지침은 스킬 설명서에 함께 들어 있어 별도 파일을 복사할 필요가 없습니다.

  • 앞 스크립트의 결과를 보고 다음 스크립트를 스스로 고릅니다.

시나리오 B · 한 줄씩 따라가기

지금 소스 위치 보여주고, 한 줄 넘긴 다음 지역 변수 알려줘
1sw_get_source.cmm
2sw_step_over.cmm
3sw_get_locals.cmm
현재 sieve.c의 반복문 시작 줄에 있습니다. 한 줄 진행한 뒤의 지역 변수를 표로 정리했습니다. 반복 변수 값이 예상과 다르면 알려주세요.
포인트
  • 스크립트 3개를 순서대로 호출합니다.
  • 앞 스크립트가 끝나야 다음이 실행되도록 서버가 보장합니다 — 겹쳐 실행되지 않습니다.

시나리오 C · 함수에서 멈춰 세우기

포인트
  • 심볼 검색 결과를 다음 호출의 인자로 그대로 씁니다.
  • MDS 검증: 실행 후 약 70ms 안에 브레이크포인트에 도달했습니다.

시나리오 D · Fault 원인 좁히기

실행하다가 Data Abort가 났어. 원인 찾아줘
1set_halted.cmm
2core_get_registers.cmm
3check_fault_status.cmm팀 추가 스크립트
4sw_get_source.cmmaddress: LR_abt − 8
Abort 모드에서 멈춰 있습니다. DFSR=0x801 — 정렬(Alignment) 오류, 쓰기 접근입니다. DFAR=0x08000001, 홀수 주소에 32비트 쓰기를 시도했습니다. 원인 명령어는 str r2,[r3]입니다. 이 명령어가 속한 함수는 호출 구조상 자동으로 특정하기 어려워, 심볼 범위로 확인하려 합니다. 진행할까요?
포인트
  • 기본 25종에는 fault 상태 레지스터 전용 스크립트가 없어, 팀에서 추가한 스크립트를 함께 썼습니다 (→ 09 확장).
  • MDS 검증(fault 이미지 13종): 유형 분류는 모두 정확했습니다. 원인 명령어는 동기(synchronous) fault 위주로 특정됐고, 소속 함수는 호출 구조에 따라 엔지니어 확인이 필요했습니다.

응답 문구는 이해를 돕기 위한 예시입니다. 스크립트 호출 순서는 MDS 검증에서 실제로 관찰한 흐름입니다.

07

잘 쓰는 요령

같은 AI라도 요청 방식에 따라 결과가 달라집니다. MDS 검증에서 효과를 본 방법입니다.

TIP 1

증상은 구체적으로

기대 동작과 실제 동작을 함께 알려주세요.

“죽었어요” → “main 진입 2초 뒤 Data Abort. 직전에 UART 초기화”
TIP 2

가설은 하나씩

AI는 가설 하나를 확인하도록 설계되어 있습니다. 중간에 방향을 확인해 주세요.

“지금 방향 맞아? 다음 가설로 넘어가기 전에 요약해줘”
TIP 3

숫자 표기 규칙

PRACTICE는 16진수 0x10, 10진수는 끝에 점 10.을 씁니다. 진법 표시가 빠지면 엉뚱한 오류 메시지가 나올 수 있습니다.

“1000. 밀리초만 실행해줘”
TIP 4

소스 파일은 절대경로로

파일 내용 조회는 정확한 절대경로가 필요합니다. 경로를 모르면 먼저 찾게 하세요.

“소스에서 sieve.c 경로를 먼저 찾고 열어줘”
TIP 5

심볼 검색은 좁혀서

전체(*)를 한 번에 요청하면 결과가 잘릴 수 있습니다. 범위를 나누세요.

“심볼 전부” → “t로 시작하는 심볼 찾아줘”
TIP 6

값의 의미는 엔지니어가

문법상 맞는 명령도 의도와 다를 수 있습니다. 결론 전에 값이 무엇을 뜻하는지 확인하세요.

예: 측정값이 호스트 시각인지 타깃 실행 시간인지
08

알아둘 한계

현재 버전(v0.3.0)에서 확인한 내용입니다. 알고 쓰면 대부분 피해 갈 수 있습니다.

스크립트가 있는 기능만

기본 25종 밖의 기능 — 트레이스 분석, RTOS 인식, 멀티코어 등 — 은 스크립트를 추가하거나 Lauterbach의 확장 스킬이 필요합니다.

→ 09 팀 스크립트 확장

실패가 성공처럼 보일 수 있음

스크립트 안의 오류가 결과 텍스트에 섞여 전달됩니다. 중요한 결과는 PowerView 화면으로 교차 확인하세요.

스크립트가 끝나지 않을 때

호출은 끊겨도 스크립트는 PowerView에서 계속 돕니다. 끝나기를 기다리거나 AI에게 중단을 요청하세요.

실행 중 화면 갱신 멈춤

스크립트가 도는 동안 PowerView 창이 갱신되지 않을 수 있습니다. 정상 동작입니다.

읽기도 흔적을 남길 수 있음

매핑되지 않은 주소를 읽으면 bus error가 fault 상태 레지스터에 기록됩니다. fault 진단 전에는 임의 주소 탐색을 피하세요.

원인 추정은 가설

AI의 결론은 검증할 가설입니다. MDS fault 검증에서도 유형 분류는 정확했지만, 원인 함수 특정은 엔지니어 확인이 필요했습니다.

09

팀 스크립트를 AI 도구로

보유한 PRACTICE 스크립트를 추가하면 AI가 쓸 수 있는 도구가 늘어납니다. 서버를 다시 빌드할 필요가 없습니다.

STEP 1

스크립트 작성

scripts/에 .cmm을 추가합니다. 결과는 PRINT로 출력하면 AI에게 전달됩니다. 맨 앞에는 머리말을 붙여 이 스크립트가 받는 인자를 선언합니다.

scripts/mem_layout.cmm 
; mem_layout.cmm — 링커 심볼과 현재 SP·PC를 출력 (ARM 예시)
; {
;   "interface": 1,
;   "strict": true,
;   "arguments": {}
; }

PRINT "bss_end="   var.address(__bss_end)
PRINT "stack_end=" var.address(__stack_end)
PRINT "sp=" Register(R13)
PRINT "pc=" Register(PC)
ENDDO
STEP 2

SKILL.md에 설명 추가

AI는 설명서를 보고 스크립트를 고릅니다. 언제 쓰는지, 인자가 무엇인지 적어 주세요. 한글도 됩니다.

SKILL.md 
#### `mem_layout.cmm`

링커 심볼 __bss_end, __stack_end와 현재 SP·PC를 출력한다.
스택 위쪽의 미사용 RAM 범위를 판단할 때 사용한다. 파라미터 없음.
STEP 3

요청해 보기

설명에 맞는 요청을 하면 AI가 새 스크립트를 선택합니다.

“스택 위쪽에 비어 있는 RAM이 얼마나 되는지 확인해줘”

예시 스크립트는 MDS 검증 환경에서 실행을 확인했습니다. 심볼 이름은 프로젝트의 링커 스크립트에 맞게 바꾸세요.

머리말은 AI가 아니라 서버가 읽습니다. AI는 설명서(SKILL.md)를 보고 스크립트를 고르고, t32mcp는 머리말을 보고 인자를 검사합니다. 그래서 AI가 인자를 잘못 기억하거나 엉뚱한 값을 넘겨도 타깃에 닿기 전에 걸러집니다. "strict": true를 적어야 strict 범위에서 실행됩니다 — 적지 않으면 거부됩니다. 인자 종류는 address(주소·심볼) · symbol(이름) · wildcard(패턴) · string(경로·자유 문자) · number(숫자) 다섯 가지이며, 직접 조건을 적을 수도 있습니다.
--skills 경로를 확인하세요. 수정한 스킬 폴더를 서버가 가리키지 않으면, AI는 새 스크립트가 있다고 믿지만 서버는 파일을 찾지 못합니다.
스크립트 작성이 처음이라면 — AI에게 맡기세요. lauterbach-trace32-skill-creator 스킬에 머리말 형식과 작성 절차가 들어 있어, 필요한 작업을 말하면 AI가 규칙에 맞는 스크립트를 만들어 줍니다. 인자를 받는 스크립트는 core_set_register.cmm 등 기본 스크립트의 형식도 참고가 됩니다.

12

자주 묻는 질문

Q실행 범위(execution policy)가 뭔가요?
AI에게 허용할 작업 범위입니다. strict는 스킬 폴더 안의 등록된 스크립트만, scripts는 임의 위치의 스크립트까지, unrestricted는 임의 PRACTICE 명령까지 허용합니다. 서버를 띄울 때 --execution-policy로 반드시 지정해야 하며, 빠뜨리면 서버가 실행되지 않습니다. 실장비에서는 strict를 권합니다.
Q스킬을 설치했는데 AI가 스크립트를 모릅니다.
스킬 폴더가 AI 클라이언트가 읽는 위치(.claude/skills/ 등)에 있어야 하고, 배치 후 클라이언트를 다시 시작해야 합니다. 서버의 --skills는 스크립트를 찾는 경로일 뿐 AI가 설명서를 읽는 경로와는 별개입니다. 두 경로를 같은 폴더로 맞추면 어긋날 일이 없습니다.
Qv0.2.x에서 올리려면 무엇을 해야 하나요?
세 가지입니다. ① 등록 명령에 --execution-policy를 추가합니다. ② 스킬 폴더 이름이 skill-trace32에서 lauterbach-trace32-debug-basic으로 바뀌었으니 새로 배치합니다. ③ 팀에서 만든 기존 .cmm은 strict에서 쓰려면 머리말을 붙여야 합니다(→ 09 팀 스크립트 확장). 도구 이름도 모두 바뀌었으므로 기존 도구 허용 목록은 다시 설정해야 합니다.
Q기본 스킬 말고 더 있나요?
저장소에는 debug-basic과 skill-creator 두 벌이 들어 있습니다. 유지보수 라이선스가 있으면 t32chat의 스킬 페이지에서 매뉴얼·트레이스·커버리지·프로파일링·RTOS 등 확장 스킬을 받을 수 있습니다. 설치 시 lauterbach-로 시작하는 스킬이 모두 교체되므로, 직접 수정한 내용은 다른 이름으로 보관하세요.
Q어떤 AI 도구에서 쓸 수 있나요?
MCP(stdio)를 지원하는 AI 에이전트라면 등록할 수 있습니다. Lauterbach의 공식 예시는 Claude Code입니다. 스킬(SKILL.md)을 자동으로 인식하는지는 클라이언트마다 다르므로 확인이 필요합니다.
QClaude 데스크톱 앱에서는 안 되나요?
데스크톱 앱의 커넥터 화면은 로컬 서버 설정 방식이 달라, MDS 검증은 Claude Code CLI로 등록해 진행했습니다. 처음 도입할 때는 Claude Code를 권장합니다.
Q비용이 드나요?
t32mcp와 기본 스킬(lauterbach-trace32-debug-basic, lauterbach-trace32-skill-creator)은 Lauterbach가 Apache-2.0 라이선스로 공개한 오픈소스입니다. TRACE32 사용 환경과 AI 서비스 이용 조건은 별도로 확인해 주세요.
Q소스코드나 데이터가 외부로 나가나요?
스크립트 실행 결과 — 레지스터 값, 메모리 내용, 소스 일부, 심볼 이름 — 가 AI 모델에 전달됩니다. 클라우드 모델인지 사내 모델인지에 따라 달라지므로 사내 AI 사용 정책을 먼저 확인하세요.
Q어떤 CPU·보드에서 쓸 수 있나요?
스크립트는 TRACE32 PRACTICE로 작성되어 TRACE32가 지원하는 환경을 전제로 합니다. 다만 레지스터 이름 등 아키텍처별 차이가 있을 수 있습니다. MDS 검증은 Cortex-R5F(TI TMS570LC4357 HDK)에서 진행했습니다.
QRemote API 포트를 바꿨어요.
등록 명령 끝에 --port <포트번호>를 추가하세요. 기본값은 20000입니다.
Q모든 프로젝트에서 쓰고 싶어요.
등록할 때 claude mcp add -s user t32mcp -- …처럼 -s user를 붙이면 사용자 전체 범위로 등록됩니다. 이때 --skills는 공통 스킬 폴더(사용자 홈의 .claude/skills 등)를 가리키게 하세요. 기본값(local)은 현재 프로젝트에만 적용됩니다.
Q사내 보안 정책상 MCP를 쓸 수 없어요.
TRACE32 Remote API를 Python 등에서 직접 호출하는 방식으로도 AI 연동을 구성할 수 있습니다. 환경에 맞는 방법은 MDS와 상담해 주세요.
